What the server sends

A chat API sends plain text, line by line.[MDN] For example:

data: {"content":"Hel"}
                                ← an empty line
data: {"content":"lo"}
                                ← an empty line

Each line ends with a line ending, the invisible character \n. In this lesson we write it out so you can see it. So the server really sends:

data: {"content":"Hel"}\n\ndata: {"content":"lo"}\n\n

Lesson 3 explains what the lines mean. Today there's one job: get the lines out, one by one, exactly as the server sent them.

The problem

Say the server sends two lines: data: hello and data: world. The network doesn't care about lines. It can deliver them as three chunks like this:

chunk 1:  "data: hel"
chunk 2:  "lo\ndata: wor"
chunk 3:  "ld\n"

If you split each chunk on \n separately, you get "data: hel", "lo", "data: wor", "ld". All four are broken pieces, not lines.

The fix: a buffer

A buffer is a string variable where text waits until its line is complete. Think of it as a waiting room.

The one rule: a line is complete only when you see its line ending. Text after the last line ending is not finished yet, so it stays in the buffer and waits for the next chunk.

Every time a chunk arrives, do three things:

  1. Add the chunk to the end of the buffer.
  2. Take out every complete line from the front of the buffer.
  3. Keep whatever is left. It's an unfinished line.

Here are the three chunks again, step by step:

Chunk arrivesBuffer after adding itLines taken outBuffer keeps
"data: hel""data: hel"none (no \n)"data: hel"
"lo\ndata: wor""data: hello\ndata: wor""data: hello""data: wor"
"ld\n""data: world\n""data: world"""

Now click through it yourself. The pink box explains each step in words:

In code, steps 1 to 3 look like this (for now, only \n endings):

buffer += decoder.decode(value, { stream: true });  // 1. add

let end;
while ((end = buffer.indexOf('\n')) !== -1) {      // is there a line ending?
  yield buffer.slice(0, end);                       // 2. take out the line (without \n)
  buffer = buffer.slice(end + 1);                   //    remove it from the buffer
}
                                                    // 3. whatever is left stays

You've seen this idea before. In lesson 1, the TextDecoder kept half a character until the rest arrived. The buffer does the same thing for half a line. Keep the unfinished part and wait for the rest: that's the main trick of reading streams.

Three kinds of line ending

Different systems end lines differently. The SSE rules accept all three, and all three mean "this line is finished":[WHATWG]

EndingNameExample
\nline feed (most common)"data: hi\n"
\r\ncarriage return + line feed (Windows style)"data: hi\r\n"
\rcarriage return alone (rare)"data: hi\r"

Important: \r\n is one line ending made of two characters, not two line endings.

The tricky case: \r at the end of the buffer

Say chunk 1 is "data: a\r". You see \r at the very end. What does it mean? There are two possibilities:

  • Chunk 2 starts with \n. Then the \r was the first half of \r\n: one line ending.
  • Chunk 2 starts with anything else. Then the \r was a line ending on its own.

You can't tell yet. So you do what you always do with unfinished things: leave the \r in the buffer and wait for the next chunk.

What goes wrong if you don't wait? You treat \r as a line ending, then chunk 2's \n looks like a second line ending. That creates a fake empty line. In lesson 3 you'll see that an empty line means "the message is finished", so a fake one breaks messages in the wrong place.

When the stream ends, no chunk can follow, so a \r at the very end is simply a line ending.

Two more rules

  • Empty lines count. "a\n\nb\n" has three lines: "a", then "" (empty), then "b". Give the empty line back too, because next lesson it means "message finished".
  • A line with no ending at the end of the stream is dropped. If the connection dies in the middle of a line, that line is incomplete. The SSE rules say to throw it away.[WHATWG]

Interview question: "Why not just split the text on \n\n to find messages?"

A good answer: "Because the two \ns can arrive in different chunks, and line endings can also be \r\n or \r. I first collect whole lines with a buffer. Then an empty line tells me a message is finished."

Practice: readLines

Hint 1: the shape

Write a small helper inside: function* takeLines(isEnd). It walks through buffer, yields each complete line, and at the end keeps only the leftover: buffer = buffer.slice(start). Call yield* takeLines(false) after each chunk and yield* takeLines(true) after the stream ends.

Hint 2: walking through the buffer 
let start = 0;                         // where the current line starts
for (let i = 0; i < buffer.length; i++) {
  const ch = buffer[i];
  if (ch === '\n') {
    yield buffer.slice(start, i);      // the line, without its ending
  } else if (ch === '\r') {
    if (i === buffer.length - 1 && !isEnd) break;   // last char: wait
    yield buffer.slice(start, i);
    if (buffer[i + 1] === '\n') i++;   // \r\n is ONE ending: skip the \n
  } else {
    continue;                          // normal character
  }
  start = i + 1;                       // next line starts after the ending
}
buffer = buffer.slice(start);          // keep only the unfinished part
