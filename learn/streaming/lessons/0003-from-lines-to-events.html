From lines to events

You can get clean lines out of a stream. Now you'll learn what the lines mean, and group them into events: the messages your app actually uses. ~20 minutes.

Your win today Write toEvents(lines), which turns lines like data: hello into events like { event: "message", data: "hello", id: "" }.

The big picture

An event is a group of lines that ends with an empty line. Here is a stream, already split into lines (lesson 2's job), and what it turns into:

Lines from the serverEvents you get
: keep-alive

event: update
id: 7
data: first line
data: second line

data: hi

nothing (a comment)

{ event: "update",
  data: "first line\nsecond line",
  id: "7" }

{ event: "message",
  data: "hi",
  id: "7" }

Notice two things. The second event has id: "7" even though it never sent an id. And its type is "message", not "update". The rules below explain both.

Four kinds of line

Every line is one of these:[WHATWG]

The line…ExampleWhat to do
is empty""The event is finished: send it
starts with :": keep-alive"A comment. Ignore it. Servers send these so the connection doesn't time out.
has a :"data: hi"Split into a field (data) and a value (hi)
has no :"data"The whole line is the field. The value is "".

Splitting field: value

Two rules:

  1. Split at the first : only. The value can contain more colons, for example JSON.
  2. If the value starts with a space, remove one space. Only one.
LineFieldValueWhy
"data: hi"data"hi"one space removed
"data:hi"data"hi"no space to remove
"data: hi"data" hi"only ONE of the two spaces is removed
'data: {"a":1}'data'{"a":1}'split at the first : only
"data"data""no : at all

Three variables, three fields

The parser keeps three variables while it reads. Each field changes one of them:

FieldVariableWhat it does
datadata bufferAdd the value and a \n to the end. Several data lines build one multi-line message.
eventevent typeSet the type. If it's never set, the event's type is "message".
idlast idSet the id. It stays for every later event until the server sends a new one.
anything elsenoneIgnore it (for example retry).

Field names must match exactly: Data: with a capital D is not data.[WHATWG]

The empty line: send the event

When you read an empty line:

  1. If the data buffer is empty, send nothing. An event with no data isn't sent.
  2. Otherwise send { event: type || "message", data, id: lastId }, but first remove the last \n from data. Every data line added a \n, so there's always one extra at the end.
  3. Either way, reset the data buffer and the event type to "". Don't reset the last id.[WHATWG]

So the type is per event, but the id carries over. That explains both things you noticed in the big picture.

One last rule: if the stream ends and the last event never got its empty line, don't send it. It might be cut off.[WHATWG] You get this for free, because you only send on an empty line.

Interview question: "What is the id field for?"

A good answer: "Resuming. The browser remembers the last id. If the connection drops, the browser's EventSource reconnects and sends it in a Last-Event-ID header, so the server can continue from there.[WHATWG] That's why the id stays after each event instead of being reset."

Practice

Write toEvents(lines). It gets an array of lines (already split, like readLines gives you) and yields events. It's a normal generator (function*), because there's no waiting yet. Lesson 4 connects it to the stream.

Practice: toEvents

Hint 1: sending an event 
if (line === '') {
  if (data !== '') {
    yield { event: type || 'message', data: data.slice(0, -1), id: lastId };
  }
  data = '';
  type = '';
  continue;
}
Hint 2: splitting field and value 
const colon = line.indexOf(':');
const field = colon === -1 ? line : line.slice(0, colon);
let value = colon === -1 ? '' : line.slice(colon + 1);
if (value.startsWith(' ')) value = value.slice(1);
